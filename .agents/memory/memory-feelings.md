---
name: Feelings-in-context — the second memory layer (Sprint 2C)
description: memory_feelings mirrors memory_facts; shares dedup + importance; flows through every fact pipeline
---
- **What it is:** `memory_feelings` stores emotional texture attached to a moment ("the Sunday family dinner made her feel small, the way it always does") — distinct from `memory_facts` which stores WHAT was said. Deliberately a near-exact mirror of memory_facts so the SAME machinery applies with no second implementation.
- **Schema** (`lib/db/src/schema/memory-feelings.ts`): `feeling` (encryptedText, AAD `memory_feelings.feeling`), `category` (emotion family: grief|shame|joy|fear|anger|love|loneliness|hope|anxiety|pride|guilt|relief|sadness|other, default "other"), createdAt, + the exact Sprint 2A importance columns (times_referenced, last_referenced_at, emotional_weight **default 0.5** since feelings carry charge, user_marked_important). `user_id` has **ON DELETE CASCADE** (the only structural difference from memory_facts, which relies on the explicit auth.ts sweep) — but auth.ts ALSO deletes it explicitly for parity.
- **Extraction** (`extractFeelings` in services/ai.ts): mirrors `extractMemory` — Haiku pass returns `{feelings:[{feeling,emotion,intensity}]}`; emotion→category (validated against KNOWN_EMOTIONS→"other"), intensity→emotionalWeight (clamped, default 0.5). Fires from `runConversationExtractions` on the SAME every-4th-user-message cadence + same last-8 window as extractMemory. Uses the SHARED `findSemanticDuplicate` (dedup sprint) — on a hit, bumps times_referenced/last_referenced_at and raises weight via GREATEST, never inserts a near-dup. Takes an optional `dedupFinder` so tests inject a deterministic stand-in. Fail-open.
- **Subject bug fix (2C follow-up):** the stored `feeling` is a full sentence shown VERBATIM (Memory.tsx + GET /memory/feelings both render `f.feeling` untouched), so any subject in it comes from extraction. The first prompt fed the user's name in as a speaker label and asked for "third person about the user", so the model wrote the user's name as the sentence subject — a mangled name like "Hi" rendered as "…, Hi felt a quiet frustration…". Fix is prompt-only, in the now-exported pure `buildFeelingsPrompt(recentMessages, companionName)`: user turns are labelled neutral `User:` (the name is NEVER passed in), and the rules DEMAND a subjectless, situation-anchored sentence (the situation carries the feeling; no name, no he/she/they/you). Going-forward only — existing rows keep their stored text (clear via the founder `/api/memory/reset` if needed; no backfill).
- **Importance:** reuses `scoreFactImportance`/`rankFactsByImportance` verbatim (they're generic `ScorableFact`). `recordMemoryReferences` (references.ts) now bumps BOTH facts and feelings when a message mentions them.
- **System prompt** (systemPrompt.ts): feelings fetched (guarded — degrades to [] on a pre-table prod), ranked (top 15), surfaced as a `feelingsBlock` pushed right after `factsBlock` ("How things have felt … hold gently, don't recite").
- **Everywhere facts go, feelings go:** account.ts `fetchExportPayload` (query + decrypt + HTML report section "How things have felt" + summary `feelingCount`); Sprint E `memoryExport.ts` (`memory.feelings` in JSON + "How things have felt" markdown section); `/api/memory/reset` wipe; auth.ts account-deletion sweep. Coverage guards (account-export JSON/HTML, account-deletion, summary-sync) were all updated — **when you add another memory table, expect these same guards to fail until you wire it into all of them.**
- **UI:** read-only `GET /api/memory/feelings` (ranked, plain JSON — no api-zod regen) + a "How things have felt" section in the Memory Manifest (Memory.tsx), fetched via raw apiFetch. `hasNoData` now includes feelings.
- **Not done (out of scope / no need):** feelings are NOT in the one-time dedup backfill (no legacy rows exist — the table is new) nor the data-encryption migration (born encrypted). stage.ts progression still keys off facts only (feelings shouldn't gate onboarding stage).
